Project 04  ·  Zennify  ·  internal

Project management office knowledge agent

A knowledge retrieval agent that answers questions about how the delivery organisation actually runs. It reads from Google Sites, Google Drive, Slack, and project documentation through a Model Context Protocol connector deployed on Google Cloud Run.

Role
Connector development and deployment
Users
Delivery leads and project managers
Pattern
Retrieval over live systems, not a copy
Runs on
Google Cloud Run

The problem

The answer existed. Finding it took knowing where to look.

How a delivery process works, which template is current, what a project agreed last quarter: all of it was written down somewhere. Spread across an internal site, a shared drive, Slack history, and project documentation, with no single index.

The people who most needed those answers were the newest, which is exactly the group least able to guess which system holds them.

The approach

Read the live systems. Do not build another copy.

A second index of the same knowledge is a second thing to keep current, and it goes stale quietly. So the agent retrieves from the systems of record at query time through connector tools, one per source.

Answers cite where they came from, which means a wrong answer points at the document that needs fixing.

Sources

Four systems of record, one question box.

Each source needed its own tool, its own permissions, and its own answer to the question of what happens when the retrieval finds nothing.

Google Sites

The internal handbook

Process pages, delivery standards, and the operating model as published to the organisation.

Google Drive

Templates and artefacts

Statements of work, plans, and the templates that a delivery lead is expected to start from.

Slack

Decisions in conversation

The channel history where a decision was actually made, often before anyone wrote it down formally.

Project documentation

What a given project agreed

Per-engagement scope, status, and commitments, so an answer can be specific to one client rather than general.

How it works

A connector, not an integration project.

The Model Context Protocol is the reason this was weeks rather than months. The connector declares what it can read; the agent decides when to read it. Nothing about the agent has to be rebuilt when a source is added.

Step one
Ask
A question in plain language, from someone who does not know which system holds the answer.
Step two
Retrieve
The agent selects the connector tools that could hold it and reads the live source, scoped by the caller's permissions.
Step three
Answer with a citation
The answer names the document or channel it came from, so it can be checked rather than trusted.
Step four
Say when it does not know
A retrieval that finds nothing returns nothing. An agent guessing about a client commitment is worse than no agent.

What it taught me

Most of the work was not the protocol.

Deployment

Containers that would not start

I resolved the Google Cloud Run container deployment failures and finalised the configuration. A connector that fails to start presents identically to one that has no tools at all, which is the least helpful failure mode there is.

Permissions

The agent should not see more than the asker

Retrieval across a shared drive and a Slack history is a permissions problem before it is a retrieval problem. The connector reads within the caller's access, not above it.

Carried forward

Absence carries no reason

Debugging this connector is where I learned that an empty tool list tells you nothing about why. That lesson became a diagnostic command in the assessment plugin, which names the missing credential instead of leaving an engineer to guess.
